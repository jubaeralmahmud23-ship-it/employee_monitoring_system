# Feasibility assessment — idea 07

**Idea title:** Documentation as Audit Evidence: How Often Do Self-Reported Model-Card Benchmark Scores Agree with Independent Evaluations of the Same Checkpoint?

**Assessed:** 2026-10-05. Source record: `research/02_candidate_ideas_merged.json`, `ideas[6]` (lens: governance-evaluation validity; `runs_without_llm: true`). This session ran on the author's local Windows 11 machine (scenario B below); the earlier cloud container is scenario A.

**Method of this assessment:** 10 WebSearch queries; 3 WebFetch reads (leaderboard documentation "About" and "FAQ" pages, the ICML 2026 virtual page of "From Claims to Compliance", the Hugging Face blog post on MMLU implementation differences); about 60 curl calls to the Hugging Face Hub API (dataset, model and space metadata, tree listings, raw READMEs, request and result files), 2 Zenodo API calls, 5 Crossref queries, 3 `gh api` repository and branch lookups, 3 PyPI JSON checks. Files actually downloaded to confirm structure: seven dataset READMEs, five result JSONs (three v1 and two v2 for `HuggingFaceH4/zephyr-7b-beta`), two request JSONs, three model READMEs (`HuggingFaceH4/zephyr-7b-beta`, `mistralai/Mistral-7B-Instruct-v0.2`, `NousResearch/Hermes-3-Llama-3.1-8B`), the Zenodo ReadMe text. Semantic Scholar answered HTTP 429 on its single attempt; the arXiv export API answered 429 (after a 301 to https) on its last two calls and empty bodies on three earlier ones, so two candidate undermining papers were identified only by title via WebSearch and not read. doi.org was not used (403 to curl); Crossref was used instead. No package was installed; no dataset was bulk-downloaded; no repository other than the working repository was cloned.

## 2. Labels and measurements (adequacy for the intended claim)

**Independent measurement.** Confirmed in the downloaded files: v1 result JSONs give `acc`/`acc_norm` and their stderrs per task and the evaluated `model_sha`; v2 result JSONs give `acc_norm,none`/`exact_match,none`/`prompt_level_strict_acc,none` with stderrs, `config.model_sha`, the harness `git_hash` and the `chat_template_sha`. Two measurement details the idea record did not anticipate:
- MMLU in v1 is 57 subtasks with individual stderrs; the leaderboard's displayed MMLU is their mean (zephyr: 0.6106 and 0.6070 in the two full runs). The stderr of the mean must be computed (independent subtasks, so the root-sum-square divided by 57), which the study can do from the file.
- v2 IFEval instance-level stderrs are `'N/A'`; prompt-level stderrs exist. v2 displayed scores are normalised ((raw − random baseline)/(1 − baseline), per the normalisation doc); the `contents` parquet carries both raw and normalised columns, so a self-report must be matched to whichever scale it uses, and this must be a coded field.

**Noise floor.** The design's plan to use "models with two result files" needs qualification from what was observed:
- v1: 2,244 of 7,121 model directories have 2 or more files, but the three zephyr files have three different `model_sha` values (`8af01af3…`, `0f17b36a…`, `dc24cabd…`), two dtypes (float16, 8bit, bfloat16) and two `lighteval_sha` values; one of them is a GSM8K-only addendum (GSM8K was added to v1 later). Between the two full runs the per-task differences are −0.3, +0.5, −0.25 and +0.8 stderr units for ARC, HellaSwag, TruthfulQA and Winogrande, but −18 stderr units for GSM8K (0.157 absolute), which is plausibly the 8-bit quantisation or a prompt/harness change rather than sampling noise. The usable noise floor is therefore the subset of pairs with identical `model_sha`, identical `model_dtype` and identical `lighteval_sha`; its size is unknown until all files are parsed (the metadata is inside the files, not in the file names).
- v2: 5,343 of 10,510 files carry one of two bulk timestamps and, for zephyr, differ only in MATH cells with a task-version bump (1.0 → 3.0). These are re-scores of stored generations, not independent re-runs, and must be excluded from the noise floor (they are, however, a clean measurement of "scoring-rule drift"). Only 444 model directories have 2 or more non-bulk files; among those, precision and sha may still differ (the FAQ says duplicates arise "under different commits or precision settings"). The genuine same-configuration replicate set may be small (tens to low hundreds). The leaderboard's own statement that results "vary slightly for different batch sizes because of padding" is the only documented source of pure run-to-run noise.
- Consequence: the noise floor should be reported in three tiers (same sha+dtype+harness; same sha, different dtype; same model name, different sha), and the GPU re-evaluation in scenario B (§3) is the only way to obtain fresh same-configuration replicates on demand.

**Self-report extraction (regex, no LLM).** Tested on three cards:
- `HuggingFaceH4/zephyr-7b-beta`: YAML front matter 4,949 characters with a `model-index` of 9 results, 7 with `source.name: "Open LLM Leaderboard"` and 2 (AlpacaEval 0.906, MT-Bench 7.34) with no `source` and a YAML comment "(taken from model card)". Body: 3 markdown tables; an author-typed comparison table with MT-Bench 7.34 and AlpacaEval 90.60 (18 rows, mostly other models, which the regex must not attribute to zephyr), and a training-log table. The six v1 benchmark names each appear once in the body, consistent with a bot-added results section. Author-typed numbers exist, but on benchmarks the leaderboard never ran, so this card yields RQ1 claims and no RQ2 pair.
- `mistralai/Mistral-7B-Instruct-v0.2`: no tables, no benchmark names, no `model-index`. Zero claims.
- `NousResearch/Hermes-3-Llama-3.1-8B`: the body contains a heading "Open LLM Leaderboard Evaluation Results" with a seven-row metric table added by the bot, while the YAML `model-index` is `results: []`. **The `source` field alone therefore under-identifies bot content**; the classifier must also match the bot's section heading and, ideally, the `leaderboard-pr-bot` commit author in the repository history (one extra API call per model, `/api/models/<id>/commits/main`, not tested here).
- Yield: 0 of 3 cards carry an author-typed number on a leaderboard benchmark. The 8 reachable models in the random request sample had no `model-index` at all. Before preregistration a pilot of about 200 cards must estimate the RQ2 yield; if it is below roughly 5 %, RQ2 shrinks to a few hundred claims across 10k cards and H1/H2 should be reframed as estimation with intervals rather than tests.
- A further classification is needed: an author-typed number that equals the leaderboard value to the displayed precision is a *copy*, not an independent self-report; the informative claims are those that differ or predate the leaderboard run. The submitted_time in the request file and the card commit dates allow a before/after ordering.

**Configuration matching.** The v1 and v2 About pages define the few-shot counts and metrics; the regex needs a table of aliases (e.g. "ARC-c", "ARC (25-shot)", "AI2 Reasoning Challenge", "hendrycksTest", "MMLU", "GSM8k", "MMLU-Pro"). The Hugging Face MMLU blog post documents why configuration matters: for LLaMA-65B, MMLU was 0.636 with the original implementation and 0.488 with the harness at commit `e47e01b`, about 15 points, with no misstatement by anyone. The headline must therefore be the verifiability profile, with discrepancy reported for configuration-matched claims only, exactly as the idea record says.

**Hand-coding.** A 300-card stratified sample coded by two coders (benchmark named, metric named, n-shot/config, harness or version, checkpoint or revision, source, bot vs author) at roughly 5 minutes per card is about 25 hours per coder. A second coder must be recruited; none exists in the current resources. Kappa thresholds should be fixed in the preregistration.

**Checkpoint identity.** Result files give the evaluated sha; the current card may post-date it. Fetching `README.md` at the evaluated sha (`/<id>/raw/<sha>/README.md`) was not tested here but is a standard Hub URL and should be used so that the self-report and the independent score refer to the same commit. For deleted repositories (about a quarter of the sample) neither the card nor its history is retrievable, so the population for RQ1 is "leaderboard models whose repository still exists", and attrition must be reported with the request-file metadata (likes, params, model_type, license) that survives deletion.

## 3. Compute and dependency assessment

**Scenario A (cloud baseline: 4 cores, 15 GB RAM, ~30 GB disk, no GPU).**
- Result files: about 20,670 JSON files, roughly 0.5 GB (v1) + 1.3 GB (v2) = about 1.8 GB, well under the "several gigabytes" assumed in the idea record. If fetched one by one under the confirmed 500-per-300-s API window this is about 3.5 hours; a `snapshot_download` or the datasets library may be treated differently by the rate limiter (not tested). Disk is not an issue.
- Cards: union of v1 and v2 model directories is at most 7,121 + 4,508 = 11,629 (the overlap is unknown; perhaps 9–10k unique). Two calls per model (`/api/models/<id>` for cardData, sha, gated, downloads, license; raw README) plus one optional commits call: 20–30k calls, 3.5–5 hours at the rate limit. Zenodo CSV (465 MB) is optional.
- Parsing: regex over ~10k READMEs and 20k JSONs in the Python standard library runs in minutes; the v2 files are 120 KB each, so a full parse is well under an hour on one core.
- Statistics (clustered regressions in statsmodels, permutation null): minutes.
- Human time dominates: pilot 200 cards (about 8 hours), coding scheme, 300-card double coding (about 25 hours per coder), reconciliation. **Machine total about 8–12 hours wall-clock; project total about 3–4 weeks of one researcher plus 25 hours of a second coder.**

**Scenario B (local: i7-14700KF, 31.9 GB RAM, RTX 5070 Ti 16 GB, 626 GB free, Windows 11, Python 3.14).**
- Everything in scenario A runs the same (network-bound, not CPU-bound).
- Optional independent re-evaluation of a few checkpoints with lm-evaluation-harness. Anchors from the downloaded files: the v2 zephyr run took `total_evaluation_time_seconds` 1,322 s (22 minutes) on the leaderboard cluster (GPU type not read from `pretty_env_info`); the v1 zephyr runs took 15,342 s (float16) and 19,502 s (8bit), about 4.3 and 5.4 hours, on the 2023 cluster (hardware not shown). WebSearch snippets give MMLU alone on a 7B model at 15–20 minutes with vLLM and about 2 hours with the plain Hugging Face backend.
- Memory: a 7–8B model in bf16 needs 14–16 GB of weights, which does not leave room for a KV cache on a 16 GB card, so same-dtype replication of bfloat16 leaderboard runs is limited to checkpoints up to about 3–4B parameters; 7–8B checkpoints can be replicated only for leaderboard entries evaluated in 8-bit or 4-bit (v1 has such entries; the zephyr 8bit run is one), or with CPU offload at a large time cost.
- Estimate (stated as an estimate, not measured): v1 six-task suite with the Hugging Face backend on this GPU, 1–4B model: 1–3 hours; 7–8B in 8-bit: 4–8 hours (HellaSwag's 10,042 items at 10-shot dominate). v2 `leaderboard` group, 1–4B: 2–5 hours. Ten checkpoints run twice (to get a same-machine replicate pair) is therefore 40–120 GPU-hours, i.e. a few days of unattended runs.
- Software caveats: `lm_eval` 0.4.13 and `torch` 2.14.1 declare `requires_python >= 3.10` (no upper bound shown), but wheel availability for Python 3.14 on Windows and CUDA support for the Blackwell-generation RTX 5070 Ti were not verified; `vllm` 0.30.0 declares `< 3.15` and is not a Windows-native package, so the fast backend is unavailable without WSL2. A separate Python 3.12 environment under WSL2 is the safe assumption. The archived v1 numbers came from a lighteval-based fork (`lighteval_sha` in the files); the current `huggingface/lm-evaluation-harness` fork branch `adding_all_changess` (2024-10-28) is what the About page points to for v2.
- What the GPU arm adds: (i) a fresh same-sha, same-dtype, same-harness noise floor from paired runs on one machine, which the archive cannot supply cleanly (see §2); (ii) a direct measurement of harness-version drift by re-running archived checkpoints at the archived `git_hash` versus the current release; (iii) a check of whether today's card numbers for a handful of popular small models reproduce. It does not change the main design, which remains archival, and it should be reported as a calibration appendix of 5–10 models.

**Does the core method need an LLM or embedding model?** No. Extraction is regex plus a hand-coded validation sample; classification of bot content uses the `source` field, the bot's section heading and the commit author. An LLM extractor would be tempting because author-typed tables are heterogeneous (row-per-model comparison tables, inline prose such as "achieves 7.34 on MT-Bench", images of tables that regex cannot read at all). The ways to keep it out or contain it: (a) treat the hand-coded 300-card sample as the gold standard and report regex precision and recall with intervals, propagating the recall bound to RQ1 estimates; (b) if an open local model is ever used as a second extractor on scenario B, it must be evaluated against the same gold sample and never used as the sole source of a number entering RQ2; (c) numbers in images are coded as "claim present, value not machine-readable" and counted in the verifiability profile, not in the discrepancy analysis. No paid API is required at any point.

## 4. Approvals and ethics

- No human participants, surveys or interviews. The second coder is a collaborator, not a subject. No IRB/ethics approval is required for the archival analysis; a departmental ethics self-assessment may still be advisable because the unit of analysis is an identifiable account's public statement.
- The data are public: leaderboard result and request files published by Hugging Face, model cards published by their authors under per-repository licences, Hub metadata via the public API.
- Naming: organisations and usernames are already public on the leaderboard and on each model page. The leaderboard population is dominated by individual accounts ("hobbyists"), whose usernames are pseudonymous personal identifiers. Proposed rule: aggregate results by organisation type (company, academic, individual) and by covariates; publish per-claim tables with model id for *organisations* (companies, labs, official providers), and pseudonymise individual accounts in released tables while keeping the mapping reproducible from the public inputs. Use "discrepancy" and "non-verifiable", not "misstatement" or "false", for any individual case; misstatement is a population-level inference about documentation reliability, not an accusation.
- Licensing of derived tables: `requests` is apache-2.0; `results` and `contents` have no licence field in either version, and v2 `results` has no README at all. Facts (scores) are not copyrightable, but redistribution of the files themselves should wait for a reply from the maintainers (a discussion on the leaderboard space is the documented channel). Model READMEs are under their repository licences; release extracted claims (benchmark, metric, value, position in card) and not the full card text. Zenodo CSV is CC-BY-4.0 (cite). Hub API use is governed by Hugging Face's terms; the confirmed rate limit must be respected.
- No sensitive content is generated or processed.

## 5. What the design can and cannot claim

**Can claim (internally valid):**
- A platform-scale verifiability profile of evaluation claims in the cards of leaderboard-evaluated models (RQ1), with extraction error bounded by the double-coded sample, and attrition reported (about a quarter of evaluated repositories are now deleted or private, by a small probe).
- For configuration-matched claims, the signed and absolute discrepancy between the card's number and the independent score for the same checkpoint sha, in stderr units, with a stratified noise floor (same sha+dtype+harness pairs where they exist; GPU replicate pairs on scenario B).
- A clean distinction between author-typed numbers and bot-populated leaderboard copies, which is itself a contribution to the Liang et al. line of work: how much of "documented evaluation" on the Hub is platform-generated.
- Associations between verifiability/discrepancy and organisation type, downloads, licence, merge/fine-tune status, release date and Flagged status (RQ3), as descriptive, clustered regressions.

**Cannot claim (or must be scoped):**
- That any discrepancy is a misstatement. The MMLU blog post shows about 15 points of implementation-driven difference on the same checkpoint; few-shot count, chat template, normalisation and harness version all move scores. The paper can say "does not agree with the independent measurement under the stated configuration" and quantify how much of the gap closes when configuration is matched; it cannot attribute intent.
- Anything about frontier or proprietary vendors. The population is open checkpoints submitted to a community leaderboard, hobbyist-heavy; the official-providers list is a small stratum. Generalisation to EU AI Act technical documentation of general-purpose AI providers is by analogy only.
- Current practice. The leaderboard was archived in March 2025 (WebSearch; the space still runs as a static table and the v2 `requests` repository still receives writes). Results describe 2023–2025 documentation practice; the Hub's 2026 first-party/third-party split means the mechanism has changed since.
- A confirmatory test of H1/H2 if the RQ2 yield is low. If author-typed, leaderboard-comparable numbers are rare (the three sampled cards had none), H1 and H2 become estimates with wide intervals and the headline reverts to RQ1 and RQ3, which the idea record already anticipates.
- A pure sampling-noise floor from the archive alone: v2 duplicate files are bulk re-scores and v1 duplicates mostly differ in sha or precision. The noise floor must be presented in tiers, and the scenario-B GPU pairs are the only same-configuration replicates under the study's control.

## 6. Blockers

1. **RQ2 yield is unknown and may be small.** 0 of 3 inspected cards and 0 of 8 random reachable models carry an author-typed number on a leaderboard benchmark (the 8 had no `model-index` at all). A 200-card pilot before preregistration is mandatory; the design must specify what happens below a yield threshold.
2. **Bot-content classification needs more than the `source` field.** Hermes-3 shows a bot-added body table with an empty YAML `model-index`; the classifier must use the bot's section heading and the `leaderboard-pr-bot` commit author as well.
3. **Noise floor from the archive is weaker than assumed.** v2 "duplicates" are re-scores (5,343 files on two timestamps; MATH version 1.0 → 3.0); v1 duplicates differ in sha/dtype (zephyr GSM8K differs by 18 stderr units across precisions). Same-configuration pairs must be counted after parsing; the GPU arm (scenario B) is the fallback.
4. **Attrition.** About a quarter of sampled request entries are deleted or private and some are renamed; the population for card-based RQs is the surviving set, and survivorship must be modelled with request-file covariates.
5. **Licence of `results`/`contents` not shown** in either leaderboard version; permission to redistribute derived files should be requested from the maintainers. Not a blocker for analysis, only for data release.
6. **Second coder** must be recruited (about 25 hours of work).
7. **Literature check incomplete:** arXiv 2503.15222 and 2606.09809 and the ICML 2026 "From Claims to Compliance" paper must be read in full; Semantic Scholar and the arXiv API were rate-limited today.
8. **Scenario B software:** Python 3.14 on Windows is untested for torch/lm_eval wheels and the RTX 5070 Ti; plan on a Python 3.12 environment under WSL2; vLLM is unavailable natively on Windows. Affects only the optional GPU appendix.
9. Minor: v2 `requests` is still changing (`lastModified` 2026-10-02), so the population must be frozen at a named commit; MMLU stderr must be derived from 57 subtasks; IFEval instance-level stderr is absent.

None of these requires money or institutional access; items 1–3 are design corrections that a one-week pilot resolves.

---

## 7. Verdict

**feasible-now.**

Reasoning: every data source exists and is reachable today without gating: both leaderboard `results` repositories (10,160 and 10,510 files, about 1.8 GB in total), both `requests` repositories (apache-2.0), both `contents` parquets with the `Flagged` and `Model sha` columns, the Hub model API with cardData and `model-index` `source` fields, raw READMEs, and the CC-BY-4.0 Zenodo metadata CSV. The result files contain exactly the fields the design needs (`model_sha`, per-task scores and stderrs, harness commit, dtype, chat-template hash). The compute is trivial on either scenario: about 3.5–5 hours of rate-limited API calls, under 2 GB of disk, and minutes of CPU for parsing and statistics; no LLM, embedding model, GPU or paid API is needed for the core method. The leaderboard's own documentation gives the configuration dictionary and reproducibility command, and the harness fork and commits are on GitHub. No approval is required. The study's weak points are substantive rather than resource-related: the number of author-typed, leaderboard-comparable claims may be small; the archive's duplicate files are not clean replicates; a quarter of the repositories are gone; and the `source`-field classifier needs supplementing. These are resolved by a pilot and by presenting the noise floor in tiers, and the scenario-B GPU can add a small, clean replicate set (40–120 GPU-hours for 10 checkpoints run twice) without changing the design. If the pilot shows almost no author-typed comparable numbers, the project remains publishable as a verifiability-and-provenance study (RQ1, RQ3), which is the fallback the idea record already names.

## 8. Minimum change in resources that would unblock the full design

Nothing beyond what is in hand is needed for the archival design. Three small additions would strengthen it: (i) a second coder for about 25 hours (double coding of the 300-card sample); (ii) a Python 3.12 WSL2 environment on the local machine so that lm-evaluation-harness and torch run on the RTX 5070 Ti for the 5–10 model calibration appendix, and, if 7–8B models in bf16 are wanted for that appendix, access to a 24 GB-class GPU for roughly 40–80 GPU-hours or equivalent cloud credit; (iii) a Semantic Scholar API key (free) to finish the undermining-evidence search that 429 responses cut short today. A reply from the leaderboard maintainers on the licence of `results`/`contents` is the only external dependency for releasing derived data, and it is a message, not a resource.
